## Editorial answer

Yes. The strongest reusable technique this week is **boundary verification with paired runtime probes**: a security policy is not proven by configuration alone. Test the exact deployed candidate with one action that must succeed and one that must fail, then correlate policy telemetry with independent final-state evidence.

A second useful mechanism is **separating destination, identity, and data policy** for outbound agent actions. Microsoft’s current Foundry guidance explicitly treats these as different questions rather than one generic “tool permission.”

## 1. Engineering Techniques

### Technique 1 — Prove policy enforcement with positive and negative runtime probes

**Signal Gate: 5/5**

**Problem.** A saved policy object proves configuration, not enforcement. A failed request is also ambiguous: the intended policy, destination application, DNS, TLS, or another network layer may have caused it.

**Technique.**

```text
same deployed candidate + same policy
        |
        +--> approved endpoint ----> must arrive
        |
        +--> unapproved endpoint --> must not arrive
                                      |
                             policy-decision evidence
                                      +
                             endpoint receipt evidence
```

Microsoft’s September 24 Foundry walkthrough recommends an Audit trial followed by a separate Enforced trial. It explicitly warns that a generic 403, DNS failure, or TLS failure is not sufficient proof of intended denial.

**Implementation details.** Use endpoints you control, synthetic payloads, redirects disabled, and the actual hosted runtime. Verify the exact deployed version. Capture both the control-plane decision and whether the endpoint received the request.

A release gate can be:

```text
deploy candidate
 -> attach policy
 -> positive probe
 -> negative probe
 -> correlate policy trace + endpoint receipt
 -> release
```

**Why it works.** It converts declarative security configuration into executable acceptance criteria and catches wrong-version attachment, rule ordering, proxy, TLS, and configuration/enforcement drift.

**Trade-offs.** Requires controlled test endpoints and environment-specific setup. Negative probes must remain harmless and owned by the team.

**Failure modes.** Happy-path-only tests; missing telemetry interpreted as success; workstation test substituted for hosted-runtime test; one mutable policy assumed to update all existing versions; non-synthetic data used in probes.

**When to use.** Network egress, sandbox boundaries, identity policy, tool allow/deny rules, and other controls where runtime behaviour can diverge from configuration.

**Evidence strength.** Strong official implementation evidence. The specific Foundry egress feature is Preview and explicitly not intended for production; the testing mechanism is transferable.

**Production impact.** Treat security boundaries like business behaviour: give them executable release tests.

### Technique 2 — Separate destination, identity, and data policy

**Signal Gate: 5/5**

**Problem.** “The agent may call this tool” is too coarse. The same tool may contact multiple destinations, use different principals, and send payloads with different sensitivity.

Microsoft’s walkthrough explicitly separates three questions: Is this the right destination? Is the caller authorized there? Is this appropriate data to send?

**Technique.**

```text
proposed outbound action
        |
destination gate
        |
identity / authorization gate
        |
data / payload gate
        |
bounded executor
        |
audit / final-state evidence
```

**Implementation details.** Normalize destination, operation, effective principal, resource scope, payload classification, redirect policy, and correlation ID before execution. Keep destination rules outside prompt text. Keep authentication/authorization independent. Apply data minimization/classification separately where needed.

**Why it works.** Reachability does not imply authorization, and authorization does not imply that every payload is appropriate.

**Trade-offs.** More control-plane work; payload classification may be imperfect; dynamic integrations can make destination policy harder.

**Failure modes.** Tool list mistaken for network policy; wildcard destinations; redirects leaving scope; shared service credentials hiding end-user authority; legitimate destination receiving an inappropriate payload; observability copying data unnecessarily.

**When to use.** Agents with HTTP, browser, MCP, email, cloud API, webhook, or upload capabilities.

**Evidence strength.** Official Microsoft implementation/security guidance. The three-gate representation is engineering synthesis.

**Production impact.** Review destination, principal, and payload independently for every external side effect.

### Technique 3 — Treat unattended triggers as durable jobs, not chat without a user

**Signal Gate: 4/5**

Microsoft Foundry Routines became GA on September 24. The lifecycle status itself is not the engineering signal. The useful architecture is the explicit decomposition into trigger, action, acting identity, connection, queueing, run history, and audit.

For each scheduled/event-driven agent define:

```text
trigger
 -> immutable event/run identity
 -> explicit acting principal
 -> bounded task scope
 -> duplicate/idempotency policy
 -> retry + terminal-state policy
 -> run history
 -> continuation only from validated state
```

Microsoft’s reminder tool remains Preview and can re-invoke the same agent/session later. Self-rescheduling therefore needs a continuation bound, deadline, or terminal condition.

**Failure modes.** Cron wrapped around an ordinary chat endpoint; duplicate events causing duplicate side effects; stale creator identity; unbounded reminders becoming polling loops; stale conversation state accumulating indefinitely.

**Production impact.** Apply ordinary distributed-systems discipline—idempotency, retries, terminal states, identity, and audit—to autonomous scheduling.

## 2. Engineering Blog Picks

### Microsoft — Control where your hosted agent connects with network egress in Foundry Agent Service

Source: Microsoft Foundry Blog, September 24, 2026.

**Practice change:** stop treating a tool allowlist as a network boundary. Keep destination policy outside agent code and verify it with both an allowed and deliberately denied request. Correlate enforcement telemetry with destination-side receipt evidence.

**Status:** the specific network-egress feature is Preview, has no preview SLA, and is explicitly not intended for production use.

### Microsoft — Foundry hosted agent isolation with Microsoft Agent Framework

Source: Microsoft Agent Framework Blog, September 22, 2026.

**Practice change:** model user identity and sandbox/session identity separately. A hosted session is compute/filesystem state, not a conversation and not a user identity. If sessions are pooled, application-owned files, caches, and database state may need partitioning by trusted user identity as well as session.

### Microsoft — Routines in Microsoft Foundry are generally available

Source: Microsoft Foundry Blog, September 24, 2026.

**Practice change:** scheduled and event-driven agents need an explicit unattended execution contract. Persist run identity and terminal outcome, choose the acting principal deliberately, define duplicate/retry behaviour, and bound self-continuation.

Repository: microsoft-foundry/foundry-samples

### Why study it

This is a compact example of turning a runtime boundary into an executable system test. A narrow diagnostic HTTP tool lets developers exercise Allow, Deny, Transform, and Rewrite behaviour through the actual hosted runtime.

### Architecture

```text
test invocation
 -> diagnostic tool
 -> hosted runtime egress layer
 -> policy decision
 -> controlled endpoint
 -> response + endpoint receipt evidence
```

### Five artifacts worth reading

1. `README.md` — test matrix, deployment paths, TLS caveats.
2. `azure.yaml` — hosted deployment/provisioning contract.
3. Agent entry point and diagnostic tool — minimal outbound seam.
4. Infrastructure/policy definitions — policy attachment outside model reasoning.
5. Transform/Rewrite exercises — rule ordering and destination-side verification.

### What it handles well

- narrow diagnostic seam;
- positive and negative probes;
- runtime rather than workstation verification;
- policy telemetry plus endpoint evidence;
- separate Audit and Enforced versions.

### What not to copy blindly

- Do not weaken TLS verification merely to make a test pass.
- Do not use arbitrary public systems as negative-test targets.
- Do not generalize a Preview control into a production guarantee.
- For CI, prefer deterministic invocation of the diagnostic path where possible instead of relying on model interpretation of free-text test commands.

## 4. Engineering Pattern of the Week — Verified outbound action boundary

**Status:** observation-only; candidate to reconcile with capability-containment guidance.

```text
task intent
 -> proposed side effect
 -> normalize action
 -> destination policy
 -> identity policy
 -> data policy
 -> allow | deny | escalate
 -> bounded executor
 -> independent runtime evidence
```

### Constraints

- policy facts live outside actor-writable context;
- reachability never implies authorization;
- authentication never implies payload appropriateness;
- redirects and transformed requests are included in the boundary model;
- the exact deployed candidate receives a negative test;
- control-plane evidence is correlated with independent final-state evidence.

### Failure modes

- tool allowlist mistaken for network boundary;
- correct destination with over-privileged identity;
- correct identity sending inappropriate data;
- redirect escaping destination policy;
- configuration inspection used as proof of enforcement;
- generic failure response treated as proof of the intended control.

### Evidence

- **Official implementation:** Microsoft’s Foundry egress walkthrough separates destination policy from authentication/data policy and demonstrates paired runtime probes.
- **Official architecture:** Microsoft hosted-agent isolation separates user identity from sandbox/session identity.
- **Engineering synthesis:** the combined boundary model is transferable beyond Foundry.

`capability -> destination -> identity -> data -> execution -> evidence`.
