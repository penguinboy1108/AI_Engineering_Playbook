# AI Engineering Practice Radar — 2026-09-04

## Executive summary

This week produced one especially strong engineering lesson for coding-agent systems: **author agent skills from measured failure evidence, not from imagined completeness**.

The clearest example came from the Microsoft SharePoint Framework team. They first ran coding agents *without* their new SPFx skill, repeated the same migration scenario several times because outputs are non-deterministic, graded both end-state execution and detailed migration correctness, then used the observed failure clusters to decide what guidance the skill actually needed. A green build alone was not enough: the agent often produced something executable while missing dependency and configuration details.

A second, lower-confidence but useful signal came from LangGraph persistence semantics and a recent issue report: state mutation APIs around checkpoints, interrupts, and resume paths should be treated like persistent data migrations. The durable lesson is to test state-history preservation and resume semantics explicitly rather than treating an `update_state`-style call as an ordinary in-memory assignment.

No durable playbook page is promoted this week. The first pattern has strong official evidence but would benefit from either another independent implementation or project validation before becoming canonical. The LangGraph state-mutation lesson remains an observation because the strongest failure evidence is an open issue rather than an official postmortem.

## 1. Engineering Techniques

### Technique 1 — Evidence-driven skill authoring

**Problem**  
Teams often write large `SKILL.md`, agent instructions, or domain prompts based on everything experts *think* the model might need. That produces long context, duplicated model knowledge, and guidance that still misses the failures that actually matter.

**Technique**  
Create a no-skill baseline first, measure where the agent fails, and add the smallest amount of domain guidance that fixes those observed failure classes.

**Mechanism**

```text
Representative task
      ↓
Agent with no domain skill
      ↓
Repeat N times
      ↓
Grade final outcome + detailed invariants
      ↓
Cluster failure modes
      ↓
Add targeted skill/reference/tool
      ↓
Re-run identical eval
      ↓
Keep only guidance with measured lift
```

**How it works**

Microsoft's SPFx team tested an upgrade from SPFx 1.21.1 to 1.22.2 without the skill. The migration is deceptively difficult because it is not just a package bump; it includes a build-tool transition and related project/configuration changes. They ran the same task five times, then graded multiple dimensions rather than merely checking whether the project built.

Their published baseline showed that every run could pass execution gates while still missing important dependency or configuration details. This is exactly the failure mode that broad “did it work?” evals hide.

The resulting skill then encoded specific rules such as:

- read the installed framework version instead of inventing one;
- map version to the correct toolchain;
- prefer deterministic, non-interactive commands;
- route upgrade work toward an existing deterministic upgrade tool;
- validate with a clean build before declaring completion;
- keep the top-level skill as a router and move detailed workflows into focused references.

**Why it works**

The model already knows a large amount of generic software engineering. The skill should therefore provide *missing constraints, authoritative local rules, and reliable tool paths*, not re-teach broad concepts. Baseline measurement exposes exactly where model knowledge is stale, ambiguous, or operationally unsafe.

**Implementation guidance**

For a new domain skill:

1. Pick 5–20 representative real tasks.
2. Run the agent without the proposed skill.
3. Repeat non-deterministic tasks several times.
4. Grade both end-state success and domain invariants.
5. Cluster recurring failure reasons.
6. Prefer deterministic tools/APIs for rules that should not be inferred.
7. Add only the instructions needed for those clusters.
8. Re-run the same eval corpus.
9. Delete guidance that does not measurably improve behaviour.

**Trade-offs**

- Requires an eval harness before the skill feels “complete”.
- Expert graders must define what correct means beyond “tests pass”.
- Some rare failure modes will not appear in a small baseline corpus.
- Domain guidance still ages and needs source/lifecycle verification.

**Failure modes**

- Writing a huge skill before establishing baseline behaviour.
- Using a single run as evidence for a non-deterministic agent.
- Grading only final execution success.
- Encoding deterministic version-selection or migration logic in prose when a trusted CLI/tool already exists.
- Adding every discovered fact to the skill instead of keeping only behaviour-changing guidance.

**When to use**

- Coding-agent skills for internal frameworks or legacy systems.
- Domain agents where versioning, policy, migrations, or business rules matter.
- Tool-use instructions where the base model frequently chooses a plausible but wrong command/API.

**When not to use**

- Very small, one-off prompts with no repeated operational value.
- Cases where deterministic automation can fully solve the task without model reasoning.

**Evidence strength:** High — official Microsoft engineering report + public implementation repository.

**Production impact:** High. This changes agent-skill development from prompt authoring into an evidence-driven software engineering loop.

Sources:

- https://devblogs.microsoft.com/microsoft365dev/behind-spfx-dev-skills-testing-what-agents-know-and-fixing-what-they-miss/
- https://github.com/SharePoint/spfx-dev-skills

### Technique 2 — Treat checkpoint state mutation as a persistent migration

**Problem**  
Long-running agent frameworks expose APIs for editing checkpointed state, replaying old checkpoints, skipping nodes, and resuming interrupts. These calls look like ordinary state updates but can change the persistent lineage and the next execution path.

**Technique**  
Wrap checkpoint mutation and resume operations in explicit state-transition tests that verify invariants before and after the mutation.

**Mechanism**

```text
Saved checkpoint
      ↓
Snapshot invariants
(messages, approvals, tool results, next node)
      ↓
Apply state mutation / fork / resume
      ↓
Read new checkpoint
      ↓
Compare lineage + state invariants
      ↓
Resume execution in isolated test
      ↓
Commit only if state and control-flow are preserved
```

**How it works**

LangGraph documents `update_state` as creating a new checkpoint rather than mutating the original checkpoint in place. The update passes through reducers and the `as_node`/`asNode` choice can alter which node executes next. Replay similarly re-executes post-checkpoint work, including LLM calls, APIs, and interrupts.

A recent LangGraph issue reports a destructive real-world failure where an `update_state(..., as_node=END)` path around an interrupt produced a new head checkpoint with an empty message history even though the parent checkpoint still contained the conversation. That report is not yet an official postmortem, so it should not be generalized as a confirmed framework defect. It is nevertheless a useful reminder that persistent-state transitions deserve their own contract tests.

**Implementation guidance**

For any checkpointed/long-running agent runtime, create tests that assert:

- message/history count and ordering;
- approval/interruption state;
- tool-call/result linkage;
- checkpoint parent/lineage;
- reducer behaviour;
- expected next node after `as_node`/equivalent;
- replay idempotency for side effects;
- state after cancellation or “dismiss” flows;
- separation between agent failure and persistence-layer failure.

Prefer a non-destructive fork or dry-run mechanism when available. Persist snapshots around manual state edits so rollback and incident analysis remain possible.

**Trade-offs**

- Adds state-fixture and persistence-test complexity.
- Framework internals can change across versions.
- Full integration tests may require a real persistence backend rather than in-memory checkpoints.

**Failure modes**

- Unit-testing graph nodes while never testing resume/cancel/update-state flows.
- Assuming a new checkpoint preserves every old channel automatically.
- Replaying side-effecting nodes without idempotency controls.
- Using `as_node` merely to “jump” control flow without asserting state lineage.

**When to use**

- Human-in-the-loop agents.
- Long-running workflows with pause/resume.
- Durable execution and recovery.
- Manual state repair or replay tooling.

**When not to use**

- Stateless single-request workflows.

**Evidence strength:** Medium — official LangGraph persistence semantics + a current community issue reporting destructive state behaviour. The incident itself remains `needs-validation`.

**Production impact:** Medium to high for systems where agent state is business state.

Sources:

- https://docs.langchain.com/oss/python/langgraph/persistence
- https://docs.langchain.com/oss/python/langgraph/use-time-travel
- https://docs.langchain.com/oss/python/langgraph/interrupts
- https://github.com/langchain-ai/langgraph/issues/8653

**Why it is worth reading**  
It shows a rare example of an official product team evaluating a coding-agent skill against actual migration correctness rather than publishing instructions and assuming they help.

- Let failure clusters decide skill content.
- Route deterministic tasks to trusted deterministic tooling instead of asking the model to recreate the algorithm.

**Why it is worth reading**  
The docs make clear that checkpoint editing, replay, interrupts, reducers, and node attribution form a persistent execution model rather than a simple mutable dictionary.

**What should change in my engineering practice?**

Treat resume, replay, and manual state editing as first-class behavioural test surfaces. Every long-running agent project should have a small state-transition regression suite before these features reach production.

## 3. Repository Deep Dive — `SharePoint/spfx-dev-skills`

Repository: https://github.com/SharePoint/spfx-dev-skills

### Why study it

This repository is small, but that is exactly why it is useful. It demonstrates a disciplined agent-skill layout for a real, version-sensitive engineering domain without turning the skill into an encyclopedic prompt.

The most transferable idea is the split between:

```text
SKILL.md
  └─ routing + global invariants
       ├─ create.md
       ├─ upgrade.md
       ├─ toolchain.md
       ├─ react-design.md
       └─ pnpjs.md
```

The router stays compact; detailed procedures live in self-contained references. Repeated deterministic rules are centralized instead of copied across prompts.

### Core abstractions

1. **Intent router** — decides which reference applies.
2. **Global invariants** — rules that every workflow must follow.
3. **Focused references** — executable playbooks for one task family.
4. **Version-aware decision rules** — read project state first, then choose commands.
5. **Deterministic escape hatches** — use trusted upgrade tooling instead of relying on model memory.

### Five files/modules worth reading

1. `plugins/spfx/skills/spfx/SKILL.md`  
   Study how routing rules and global invariants are kept separate from long instructions.

2. `plugins/spfx/skills/spfx/references/upgrade.md`  
   Look for how upgrade work is routed toward deterministic tooling and validation.

3. `plugins/spfx/skills/spfx/references/toolchain.md`  
   A good example of centralizing version-dependent command rules rather than duplicating them.

4. `plugins/spfx/skills/spfx/references/create.md`  
   Shows requirement gathering, non-interactive commands, and validation-before-done behaviour.

5. `todo.md`  
   Despite the name, it serves as a useful design record explaining why the skill was restructured and what rules were promoted into shared guidance.

### How it handles common engineering concerns

**State/context**  
It reads project metadata such as installed framework version rather than assuming current defaults.

**Tools**  
It favors explicit CLIs and deterministic upgrade commands for steps where model inference is unnecessary.

**Retries**  
Not a major abstraction in this repository; retry/backoff remains agent-host responsibility.

**Observability/evals**  
The companion Microsoft engineering article provides the strongest evidence. The repository itself does not yet expose a full reusable automated eval harness.

**Persistence**  
Not applicable; these are coding-agent skills rather than a long-running runtime.

**Security**  
The repo emphasizes explicit commands, no invented APIs/versions, and human review before shipping. It is not a security sandbox implementation.

### Elegant choices

- Small router, detailed references.
- “Never invent versions” becomes a process rule: inspect project metadata.
- One canonical toolchain reference prevents instruction drift.
- Non-interactive commands reduce agent hangs and ambiguous terminal state.
- Clean-build validation defines a concrete completion gate.

### Choices not to copy blindly

- Domain-specific defaults such as PnPjs are correct for SPFx but should not become generic agent rules.
- Markdown-only validation is not enough for a larger skill library; production internal skills should have automated scenario evals and version/source freshness checks.
- A clean build is necessary but, as the Microsoft article demonstrates, insufficient as the only grader.

### Reusable patterns to lift into other projects

- Router + focused reference architecture for skills.
- Inspect-before-infer rules for versioned environments.
- Deterministic tool delegation.
- Baseline/failure-driven skill authoring.
- Multiple graders: executable outcome + domain-specific invariants.

### 30–60 minute reading route

**0–10 min:** README + directory structure.  
**10–20 min:** `SKILL.md` and global rules.  
**20–30 min:** `upgrade.md` + `toolchain.md`.  
**30–40 min:** `todo.md` to understand the design rationale.  
**40–60 min:** Read the Microsoft engineering article and map each observed baseline failure to the instruction/tool that was added.

### Watchlist

- `langchain-ai/langgraph` — continue tracking persistence/state-transition semantics and the open state-loss report before promoting any new durable guidance.
- `microsoft/agent-framework-go` — newly public-preview Go implementation; interesting for cross-language abstraction design, but too early and incomplete to promote this week.

## 4. Engineering Pattern of the Week

# Baseline → failure cluster → minimum skill → regression

### Problem

Agent instructions grow through intuition and accumulation. This increases context cost but does not guarantee better behaviour.

### Pattern

```text
1. Baseline without skill
2. Repeat representative tasks
3. Grade end state + hidden invariants
4. Cluster recurring failures
5. Add the minimum instruction/tool/reference that addresses each cluster
6. Re-run the identical eval corpus
7. Keep only changes that improve measured behaviour
8. Add newly discovered failures to the regression set
```

### Constraints

- Baseline tasks must resemble real work.
- Graders must check domain correctness, not just surface success.
- Changes to the underlying model require periodic re-baselining because model-native knowledge changes.
- Deterministic rules should be implemented as deterministic tools when possible.

### Trade-offs

This approach takes longer than writing a skill by intuition, but produces smaller prompts, clearer provenance, and measurable justification for every rule.

### Failure modes

- Designing the eval after the skill, which biases the grader toward the chosen instructions.
- Expanding a skill because one anecdotal run failed.
- Optimizing only the happy path.
- Leaving obsolete rules in the skill after models/toolchains improve.

### Evidence

Strong official Microsoft evidence from the SPFx Dev Skills evaluation process and public skill repository.

### Promotion decision

**Observation-layer only this week.** This is a strong candidate for a canonical playbook pattern after either project validation or a second independent production implementation confirms the same approach.
